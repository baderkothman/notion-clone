# Database

PostgreSQL 16, accessed through Drizzle ORM (`packages/database`). Schema is split into
domain-scoped files under `packages/database/src/schema/`, all re-exported from
`schema/index.ts`. Migrations are generated by `drizzle-kit` and committed to
`packages/database/src/migrations/`.

## Entity overview

```
users ──< workspace_members >── workspaces ──< workspace_invitations
  │                                  │
  │                                  └──< pages (self-referencing parent_id, tree)
  │                                         │
  ├──< favorites >───────────────────────────┤
  ├──< page_shares >─────────────────────────┤
  │                                          ├── documents (1:1, block content)
  │                                          ├──< comments >── comment_mentions
  │                                          ├──< page_revisions
  │                                          ├──< database_properties >── database_row_values
  │                                          ├──< database_views
  │                                          └──< files
  ├──< password_reset_tokens
  ├──< calendar_events (workspace calendar — see "Calendar & Google Calendar sync"
  │                      in docs/ARCHITECTURE.md; NOT the database_views calendar type)
  ├──< google_calendar_connections (one per user, scoped to one workspace — see below)
  └──< sessions / accounts / verification_tokens  (Auth.js schema shape, reserved for a
                                                     future OAuth *login* provider — see
                                                     packages/auth/src/config.ts; unrelated
                                                     to google_calendar_connections, which
                                                     is a separate, stricter-encrypted
                                                     integration-token store, not a login
                                                     mechanism)
```

## Key design decisions

**Documents live outside `pages`.** `documents.content` (jsonb, the Tiptap doc) is a
separate table keyed by `pageId`, not a column on `pages`. The autosave path writes to
`documents` every few seconds during active editing; page-tree queries (sidebar,
breadcrumbs) never load that JSON. See `documents.version` — every autosave write is a
conditional `UPDATE ... WHERE version = $expected`, the optimistic-concurrency guard
described in `docs/PRODUCT_SPEC.md`.

**A database row is a page.** There's no separate `rows` table. `pages.type = 'database'`
marks a database page; its rows are ordinary child pages (`parent_id` = the database
page's id). `database_row_values` holds one row's value for one property, sparse (no
value row until a cell is actually set). This means rows get titles, icons, comments,
sharing, and the block editor for free — the same machinery as any other page.

**Sibling ordering is a fractional index, not an integer position.** `pages.sortKey`,
`database_properties.position` (integer, low cardinality — fine as an int), and
`database_views.position` use different strategies deliberately: page/row ordering
changes frequently and needs O(1) reordering (see `packages/shared/src/sort-key.ts`,
wrapping the `fractional-indexing` library), while property/view ordering changes rarely
enough that a plain integer with periodic renumbering is simpler and was not worth a
second fractional-index type.

**Permissions are two columns plus one table, not a matrix.** `pages.visibility`
(`private`/`workspace`) and `pages.workspaceShareRole` handle the common case;
`page_shares` handles per-user (including guest) overrides. See
`apps/web/src/server/permissions/resolve-core.ts` for the precedence rule and
`docs/SECURITY.md` for the authorization model this schema supports.

**Search is a denormalized side table**, not a generated column on `pages`, because the
plain-text extraction from Tiptap JSON is application logic (walking the doc tree), not
something Postgres can compute inline. `search_documents.tsv` is a `tsvector` with a GIN
index, recomputed on the title/body write paths (`apps/web/src/server/search/index-page.ts`).

**History is coalesced, not append-only-per-keystroke.** `page_revisions` gets a new row
at most once per 5-minute window per page during active editing
(`apps/web/src/server/history/snapshot-policy.ts`), not once per autosave tick. Older
snapshots are thinned opportunistically every time a new one is taken — no scheduled
job/cron needed — to one per hour beyond 24h and one per day beyond 30 days
(`apps/web/src/server/history/prune-revisions.ts`; the bucketing decision itself is a
pure, unit-tested function in `prune-revisions-core.ts`).

**Calendar events are their own table, not database rows.** Unlike a Notion-style
database (where "a row is a page" — see above), `calendar_events` doesn't reuse the
`pages` machinery: an event has no block content, no page hierarchy, and needs a
tight `(workspace_id, start_at, end_at)` range index a generic page table can't offer.
`google_calendar_connections` is one row per user (unique on `user_id`) but carries its
own `workspace_id` — a Google account is personal, but the connection itself is scoped
to a single workspace to keep `(google_connection_id, google_event_id)` unambiguous; see
`docs/ARCHITECTURE.md`'s "Calendar & Google Calendar sync" for the full reasoning and
`docs/SECURITY.md` for how the OAuth tokens are stored.

## Indexing

Every foreign key that's queried directly has a matching index:
`pages(workspace_id, parent_id)`, `pages(workspace_id, is_archived)` (trash/sidebar
queries), `page_shares(user_id)`, `comments(page_id, created_at)`,
`page_revisions(page_id, created_at)`, `audit_events(workspace_id, created_at)`,
`calendar_events(workspace_id, start_at, end_at)` (the exact shape a month/week/agenda
view's range query needs), `calendar_events(google_connection_id)`, and the GIN index on
`search_documents.tsv`. See the migrations
(`packages/database/src/migrations/0000_slim_warstar.sql`,
`0001_fearless_steve_rogers.sql`, `0002_goofy_penance.sql`) for the full list.

## Transactions

Multi-row writes that must be atomic use `db.transaction(...)`: workspace creation +
first membership row (`create-workspace.ts`), invitation acceptance + membership row
(`members.ts`), page duplication's recursive clone, and history restore (snapshot the
current state, then overwrite).

## Cross-workspace isolation

Every table that scopes to a workspace either has a direct `workspace_id` FK
(`pages`, `files`, `audit_events`, `search_documents`) or is reachable from one through a
single join (`documents`, `comments`, `page_shares`, `database_*` — all keyed through
`pages.workspace_id`). No query in the codebase selects from `pages` (or anything joined
to it) without either an explicit `workspace_id` filter or a `page_shares`/permission
check that implicitly scopes to a workspace the requester belongs to — see
`docs/SECURITY.md` "Tenant isolation" for how this is tested.

## Local commands

```
docker compose up -d           # Postgres (5433) + MinIO (9000/9001)
pnpm db:generate                # after editing packages/database/src/schema/*
pnpm db:migrate                 # apply pending migrations
pnpm db:studio                  # Drizzle Studio
pnpm db:seed                    # optional demo account (demo@example.com)
```
